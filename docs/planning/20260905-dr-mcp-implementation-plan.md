## 1. この計画の使い方

設計仕様書を要件・挙動の正本として、ここに定義する依存関係順に実装する。各タスクは単独のコミットまたはレビュー可能な変更単位にする。Issueを作る場合も、仕様をIssue本文へ重複して固定せず、仕様の要件IDと本計画のタスクIDを参照する。

実装者は未完了の依存を飛ばして「たぶん動く」下位APIを増やさない。実機が不要な契約・状態管理・MCP層は、無料版の実機環境がなくても進められる。実機依存部分が未確認なら、該当タスクをblocked_environmentにし、依存しない作業を続ける。利用者へのバージョン番号の問い合わせを着手条件にしない。

### 進捗状態

| 状態 | 意味 |
| --- | --- |
| `not_started` | 未着手 |
| `in_progress` | 実装または確認中 |
| `blocked_environment` | 実機・依存環境がなく、そのタスクの確認を完了できない |
| `blocked_capability` | 実機で必要な能力が成立せず、設計上の解決が必要 |
| `ready_for_live` | ローカルのコード・契約試験は完了、実機確認待ち |
| `done` | タスクの完了条件と必要な検証をすべて満たした |

実機テストを要するタスクをready_for_liveのままdoneにしない。文書を作成したことと、実装が完成したことを区別する。

## 2. マイルストーンと依存関係

| 段階 | 目的 | 主依存 | 完了時に確認できること |
| --- | --- | --- | --- |
| P0 | Mac無料版の実現性確認 | なし | 起動・接続・API実行・UI応答・基本補正の経路 |
| P1 | 契約と実装基盤 | 本仕様 | 型・状態・操作履歴・MCPの試験基盤 |
| P2 | 橋渡しと機能検出 | P0、P1 | バージョン申告なしで接続と機能診断 |
| P3 | 対象参照とプレビュー | P2 | 対象を一意に特定し、その画像を取得 |
| P4 | 基本編集 | P3 | 指定区間・順序・尺・音声を保持したタイムライン |
| P5 | 基本色補正と復帰 | P0、P3、P4 | 管理対象の4項目補正、比較、復帰 |
| P6 | 書き出しと異常復旧 | P4、P5 | 指定出力の実ファイル検査、切断後の状態整合 |
| P7 | 導入と一巡検証 | P2〜P6 | Mac無料版で、チャット編集から出力までの実証 |

P1はP0の実機確認と独立して進めてよい。P2の通信処理も契約を使って先に実装できるが、Resolve内での実行文脈はP0の確認結果を使う。以下は作業の依存を示し、複数エージェントの起動を要求するものではない。

## 3. P0：無料版の実現性を確認する

### DR-T001：環境検出と起動プローブ

- 対応要件：DR-001、DR-002、DR-003、DR-015。
- 入力：Mac上のアプリ配置、ユーザー領域、既存Python。バージョン番号の手入力は不要。
- 実装：アプリ候補の検出、plist読取、CPU／Python情報の取得、Python認識とScripts表示を区別するプローブ。
- 成果物：`scripts/probe_environment.py`、`bridge/probe.lua`、`docs/compatibility/yyyymmdd-macos-free-build-verification.md`（日付とbuildは実測値へ置換）。
- 検証：アプリなし、複数候補、Python未認識、版取得不能を別状態で返す。可能な環境では無料版内から製品名・版・現プロジェクト名を取得する。
- 完了条件：Mac無料版で起動経路を確認し、実行したコマンド／メニュー、環境、結果を個人情報を除いた記録に残す。

### DR-T002：常駐・API実行文脈・補正の実機スパイク

- 依存：DR-T001。対応要件：DR-001、DR-004、DR-007、DR-010、DR-014。
- 実装：固定のhealth・読取要求だけを受ける橋渡しスパイクと、検証用プロジェクトでの色補正プローブ。
- 確認すること：受信中もResolveの再生・UI操作が応答すること、APIを実行できるスレッド／イベントループ、停止後に待受・プロセスが残らないこと。
- 色の確認：元の版の保持、新ローカル版の作成・引継ぎ、CDL適用、保存、元の版への復帰を同じクリップで試す。管理ノードを準備できる実際の経路を記録する。
- 成果物：`bridge/probe_runtime.py`、`tests/live/probe_color.py`、環境記録への結果と採用方式の追記。
- 完了条件：無料版でUI応答、読み取り、版の保存・復帰、画の変化を確認できる。Studioでしか通らない場合はblocked_capability。

起動候補はPythonのScripts経路、次に同環境で公開されているコンソール等のアプリ内経路の順に、各1回の基本診断と原因に基づく修正1回まで調べる。原因を特定できなければ繰り返さず、観測と不足を記録する。未知のOS設定を総当たりで変更しない。

P0の結果で、無料版の内部経路が利用できない場合は、そのエディションの制限を解除するコードを作らない。公開されている別の操作経路の再設計が必要と明記し、独立したP1へ進める。

## 4. P1：契約と実装基盤を作る

### DR-T003：パッケージと通信・ツール契約

- 対応要件：DR-003、DR-008、DR-012、DR-014、DR-015。
- 実装：`pyproject.toml`、依存lockfile、`src/dr_mcp/contracts/`、MCPサーバー骨格、CLI入口、単体・統合テストの配置。
- 契約：仕様書の要求／応答、feature状態、対象ID、全エラー、編集segment、色patch、操作状態をモデル化する。未定義キーを拒否する。
- SDK：採用する公式Python SDKの版を確認して固定する。会話中の試作が使ったSDK版を無条件に継承しない。
- 検証：入力の型・必須項目・不正値と、実際のMCPクライアントライブラリによる起動・tools/list・一つの読取ツール・画像応答を確認する。
- 完了条件：Resolve未接続でもMCPサーバーが起動し、明確な未接続応答を返す。stdoutをログで汚さない。

### DR-T004：操作履歴と再送・復帰モデル

- 依存：DR-T003。対応要件：DR-010、DR-012、DR-013。
- 実装：SQLite schema／migration、operation IDと要求ハッシュ、前後状態・snapshot、状態遷移、結果照会。
- 検証：同一要求の再送、同一IDで別要求、実行開始前停止、API成功直後の記録失敗、完了応答消失、再起動後の照合。
- 完了条件：実行結果が不明な変更を自動再実行せずuncertainにできる。partialと完全な復帰を区別できる。

P1終了時に将来コマンド契約を実装する。想定は `dr-mcp doctor --json`、`dr-mcp serve`、`dr-mcp self-test --live`。これらは本計画作成時点では存在せず、READMEの利用手順には実行確認後に追加する。

## 5. P2：橋渡しと機能検出を実装する

### DR-T005：認証付きloopback橋渡し

- 依存：DR-T002、DR-T003、DR-T004。対応要件：DR-001、DR-004、DR-013、DR-014。
- 実装：`bridge/dr_mcp_bridge.py`、固定actionディスパッチ、認証、キュー、bridge側実行記録、session ID、終了処理。
- 通信：仕様書の署名式・ヘッダー・期限・nonce・上限を実装。要求はbytesで検証してからJSONとして処理する。
- 検証：不正署名、nonce再利用、期限切れ、Origin、Host不一致、未定義action、本文超過、同時変更、応答消失、橋渡し再起動。
- 完了条件：許可された読取・変更だけが直列実行される。重い処理はoperation IDを返し、ResolveのUIを止めない。鍵や素材の内容がログへ漏れない。

### DR-T006：接続アダプターとcapabilities

- 依存：DR-T005。対応要件：DR-002、DR-003、DR-012、DR-015。
- 実装：接続前の環境検出、health、接続後の情報取得、API差分アダプター、feature registry、互換性記録。
- 検証：版unknownでも読取可能、メソッドらしく見えるが実呼出失敗、機能欠落、再接続でsession変更、更新による検証記録の失効。
- 完了条件：版・API存在・検証結果を混同せず、利用者のバージョン入力なしで利用可能／未確認／不可を説明できる。書込プローブを通常doctorに混ぜない。

## 6. P3：対象参照とプレビューを作る

### DR-T007：素材・タイムライン・クリップの参照

- 依存：DR-T006。対応要件：DR-005、DR-012。
- 実装：一覧ツール、ページング、安定ID、代替ID、正規化した範囲とfps、関連音声、revision token。
- 検証：同名素材、同名クリップ、同時刻の別トラック、タイムライン切替、並べ替え、削除後の古いID、欠落素材。
- 完了条件：操作対象を一意に特定でき、古い前提をCONTEXT_CHANGEDとして拒否できる。未知のID・値を推測で補完しない。

### DR-T008：指定クリップの画像取得

- 依存：DR-T007。対応要件：DR-004、DR-009。
- 実装：clip内frame offsetからseekし、実対象を確認して取得する`preview_clip`、RGB8からPNGへの変換、画像応答、前後比較の保存。
- 検証：1フレーム、クリップ終端、空き区間、別クリップへの手動移動、タイムコード境界、古いキャッシュ、取得非対応。
- 完了条件：チャットクライアントが画像を受け取り、実際のclip ID・位置・方式が一致する。同フレームの前後比較ができる。更新確認不能を隠さない。

## 7. P4：基本編集を実装する

### DR-T009：素材取り込みと編集計画

- 依存：DR-T007。対応要件：DR-005、DR-006、DR-014。
- 実装：作業ルート検証、素材の取り込み結果照合、split／trim／delete／reorderを最終segment列へ正規化するplanner。
- 検証：1フレーム区間、最終フレーム、不正区間、重複指定、fps不一致、秒指定の丸め、VFR、リンク音声、symlinkの逸脱、部分import。
- 完了条件：計画はResolveを変更せず生成でき、尺と配置が決定的に計算される。読めなかった素材を除外して全件成功としない。

### DR-T010：新タイムラインへの適用と復帰

- 依存：DR-T008、DR-T009、DR-T004。対応要件：DR-006、DR-010、DR-012、DR-013。
- 実装：元タイムラインを保持し、plan hashとrevisionを照合して作業タイムラインへ構築。結果の範囲・順序・尺・関連音声を読戻し、保存する。
- 検証：途中API失敗、保存失敗、別タイムラインへの手動切替、再送、音声脱落、未対応エフェクト、既存複雑グレード、構築後のID変化。
- 完了条件：単純なタイムラインの基本編集を正しく再構築し、失敗時に元へ戻せる。保持できない要素があれば適用前に拒否する。

P4では未対応のグレードを持つクリップの再構築を通さない。P5後にMCP管理グレードの引継ぎを追加し、「色を付けた後に再編集する」経路も検証する。

## 8. P5：4項目の色補正を実装する

### DR-T011：決定的な色変換と管理状態

- 依存：DR-T003、DR-T004、DR-T002。対応要件：DR-007、DR-008、DR-013。
- 実装：本仕様の`cdl_basic_v1`、入力検証、absolute patch、未指定値の継承、backend版管理、管理値とnative値の区別。
- 検証：中立変換、コントラスト中点、暖色／寒色の方向、彩度0、入力境界、NaN／Infinity／bool、再送、再起動後のpatch継承。
- 完了条件：同じ入力から同じ係数を生成する。Kelvin／EV／標準パネル値を独自値へ黙って置換しない。

### DR-T012：実機への適用・比較・復帰・再編集

- 依存：DR-T008、DR-T010、DR-T011。対応要件：DR-007、DR-008、DR-009、DR-010。
- 実装：P0で確認した補正先準備、元の版保持、CDL適用、保存、同フレーム画像取得、snapshot復帰。管理グレードのタイムライン再構築時の引継ぎ。
- 実機素材：生成可能なグレースケール・RGBパッチ・低コントラスト素材と、非公開で試験する短いSDR動画。
- 検証：各軸、組合せ、明るさ変更後の彩度patch、同じ要求の再送、2段階復帰、手動版切替、画像更新、再編集後の画の保持。
- 完了条件：Mac無料版で4項目の指定方向の変化と元状態への復帰を確認できる。単一ノードを無補正と誤認しない。管理外グレードと不明な色空間を安全に拒否する。

画像検証では非クリップ領域のグレーパッチ中央値、RGBパッチのチャンネル差、明暗パッチ差を指標にする。数値の許容誤差は出力bit深度とcodecに合わせ、最初の実機校正結果を環境記録へ固定する。期待値をテスト実行時の結果に追随させて合格へ変えない。

## 9. P6：出力と異常復旧を完成させる

## 12. 検証と証拠の保存

| レベル | 対象 | 合格で言えること |
| --- | --- | --- |
| 単体 | 色係数、フレーム計算、状態遷移 | 内部ロジックの確認 |
| 統合 | stdio、認証、プロセス間通信、永続化 | MCP／橋渡しの契約と障害処理の確認 |
| 実機 | Mac無料版の実際のAPI・UI・画・ファイル | 記録した環境での操作成立 |

CIはまず単体と統合を担当する。通常のクラウドCIにResolve実機があると仮定しない。実機テストは明示して起動するコマンドとし、専用の検証プロジェクト・素材・出力先を使う。元のプロジェクトを保存し、最後に元の選択へ戻す。失敗時は記録を確保してから、自分が作成した検証データだけを削除対象にする。

検証記録にはタスクID、対象commit、日時、OS／CPU、Resolve製品名・build、Python版、MCPクライアント・SDK版、前提設定、実行手順、期待結果、実測結果、成功／失敗、残った制約を含める。鍵、個人素材、ユーザー名を含むローカルパスは公開しない。

## 14. 実装者の作業手順

1. README、本仕様、対象タスク、既存コードと現在の検証記録を読む。
2. 未完了の依存を確認し、着手するタスクをin_progressにする。
3. 入出力と失敗条件を確認し、未検証のAPI契約があればまずプローブする。
4. 対象タスクの成果物を実装し、関係する検証を行う。
5. 変更した仕様があれば設計の正本に反映し、要件・テストとの対応を更新する。
6. 実行結果と未解決事項を記録し、必要な確認が終わったタスクだけdoneにする。
7. レビュー可能な単位でコミットし、依存が満たされた次のタスクへ進む。

一つの環境問題を無期限に試行しない。原因に基づく修正と再試験は同じ失敗について最大2回を初期上限とする。それでも解消しなければ再現手順・試した修正・不足能力を記録し、独立した作業へ移る。新しい根拠が得られた場合は、その根拠を添えて再開できる。

完成後に実際に通した導入コマンド、配布物、対応表をREADMEへ追加する。設計上のコマンドや存在しないモジュールを、利用者が今すぐ実行できるものとして案内しない。
